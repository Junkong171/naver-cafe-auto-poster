# 새 기능 명세 작성과 승인

요청한 기능: $ARGUMENTS

이 절차가 끝나기 전에는 `cafe_poster.py`와 예시 파일을 수정하지 않는다.

## 1. 현재 상태 파악

1. `CLAUDE.md`의 규칙과 금지 목록을 확인한다.
2. `작업기록.md`의 "지금 상태"와 "할 일"을 읽는다. (이미 결정된 일을 다시 묻지 않기 위해)
3. 관련 코드를 읽는다. 추측하지 말고 실제 코드(`파일:줄`)를 근거로 한다.
4. 네이버 API 동작에 기대는 기능이면, 그 동작을 어떻게 확인했는지(문서, 이전 실험, `log.txt`) 적는다. 외부 서비스를 새로 쓰면 무료 플랜에서 필요한 기능이 되는지 먼저 확인한다.
5. 작업 브랜치인지 확인한다. main이면 사용자에게 새 브랜치 이름을 제안하고 승인받는다.

## 2. 명세 파일 만들기

1. `docs/specs/`에서 가장 큰 F 번호를 찾아 다음 번호를 쓴다. (없으면 F-001, F-001 다음은 F-002)
2. `docs/specs/_TEMPLATE.md`를 바탕으로 `docs/specs/F-xxx-<짧은-영문-이름>.md`를 만든다.
3. 모든 항목을 채운다.
   - 수용 기준은 코드 위치, 명령 출력, `log.txt` 줄, 미리보기 화면처럼 확인할 수 있는 문장으로 쓴다.
   - 게시 영향: 실제 글 내용·게시 시각·게시 횟수가 바뀌는지, 다음 정시 글부터 적용되는지 쓴다.
   - 비범위: 이번에 하지 않을 것을 분명히 쓴다.
4. 명세는 GitHub 공개 저장소에 올라간다. Client ID/Secret, 토큰, 개인 정보, 실제 카페·게시판 ID는 쓰지 않는다.
5. 상태는 "초안"으로 둔다.

## 3. 사용자에게 보여주기

한국어로 다음을 보여준다. 어려운 용어에는 짧은 풀이를 붙인다.

1. 명세 파일 경로
2. 목적과 수용 기준 목록
3. 게시 영향 (다음 00:00 / 12:00 글이 어떻게 달라지는지, 중복·누락 위험)
4. 바꿀 파일과 대략적인 변경 내용
5. "이대로 진행할까요?" 질문

## 4. 승인 후

1. 사용자가 승인하면 명세의 상태를 "승인됨"으로 바꾼다.
2. 수정 요청이 있으면 명세를 고치고 3단계를 다시 한다.
3. `작업기록.md`에 결정 내용을 적는다.
4. 구현이 끝나면 `/verify-feature docs/specs/F-xxx-....md`로 검증한다.
